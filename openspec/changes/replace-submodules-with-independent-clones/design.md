# Design

## Context

See [the proposal](proposal.md#why) for the two-computer workflow. Today `workspace-state.ts` and `alias-preparation.ts` determine eligibility from root registrations. `sync-workspace.ts`, `repo-ops.ts`, and the root transaction code add, remove, and record gitlinks. An initialized submodule often has a `.git` file pointing into the root Git directory; its linked worktrees depend on that same repository data. Removing the root gitlink and moving the local Git directory are separate operations. A root commit can distribute the first but not the second.

## Goals / Non-Goals

**Goals:** Keep one canonical source path and eligibility model across commands. Isolate legacy conversion from normal commands. Make the migration preview, interruption recovery, and second-computer workflow safe to exercise with real local Git repositories.

**Non-Goals:** Do not retain a selectable submodule mode, add a lockfile for source commits, synchronize local branches across computers, or migrate non-OMS submodules.

## Decisions

### Keep the manifest and replace the normal checkout model

`oms.yaml` remains the source of aliases, remotes, and baseline branches. Keep the workspace Git root and `oms/<alias>/` layout. Use root-anchored, alias-specific ignore rules: migration records shared rules in root `.gitignore`; normal provisioning uses `.git/info/exclude` when no effective shared rule exists. Check the effective rules with the proposed changes before writing. If a user-authored rule defeats coverage, report the affected path without overriding the rule. Clone skips that alias; migration rejects the entire plan. Never ignore `oms/` wholesale or register sources in the root index.

Give checkout inspection one interface that reports a verified independent checkout, a missing checkout, legacy state requiring migration, or a blocked path with a diagnostic. Validate the canonical directory and actual Git top-level and Git directory rather than accepting the first successful `git` probe, which may have found the parent workspace. Do not follow symlinks out of the managed layout, treat linked task trees as canonical clones, or accept paths the root tracks as ordinary sources. Check for recognized legacy artifacts even when the checkout path is absent. Use this interface for preparation, status, doctor, `exec`, and removal; callers select policy, not filesystem heuristics. Keep the existing Git runner seam; use real local Git for lifecycle and migration tests. A registration adapter for both old and new layouts would preserve the obsolete behavior in every caller.

Accept a user-created clone at the canonical path without registration if it passes those checks and has one unambiguous `origin`. Use Git's fetch URL resolution for both that origin and the manifest URL in the same repository context, without contacting the remote. Compare the resolved strings exactly. A mismatch or missing origin blocks checkout use, remote reconciliation, and removal; report the discrepancy instead of guessing that HTTPS and SSH addresses name the same repository.

### Keep provisioning separate from branch updates and removal

`oms clone` accepts explicit aliases or `--all`. Without either it offers selection only in a terminal; cancellation leaves checkouts unchanged. Clone missing sources into temporary siblings using the declared origin and branch, or the remote default. Configure declared remotes and verify the clone before moving it into place. Recheck the destination, publish without clobbering it, and clean up only the temporary path created by this invocation. Report existing verified checkouts without fetching, attaching, or rewriting them. Explicit source commands retain their existing branch, pull, and remote-refresh policies after eligibility checks. Eligible interactive commands delegate missing checkout creation to the same operation after consent; `exec` never prepares.

Publish a verified temporary clone by exclusively creating the destination directory, installing the working files without replacing entries, and moving the prepared `.git` directory into place last. The destination remains ineligible until that last step. If the process is interrupted, inspect the canonical and temporary directories, move any partial directory aside without discarding its contents, and retry `oms clone`. OMS does not adopt or overwrite an incomplete directory.

`oms remove` requires explicit aliases or `--all`, and leaves declarations and ignore rules in place. If an alias is declared now, only that declaration establishes checkout identity. A checkout matching an older origin is preserved even when the alias was reused. For aliases absent from the current manifest, verify the declaration immediately before its removal in the history reachable from root HEAD, then apply the same identity checks. Ambiguous or missing evidence blocks an explicitly named alias. With `--all`, label verified former source checkouts separately and report unidentified paths as preserved.

Keep `oms status` source inventory, including JSON `repos`, limited to current declarations. `oms doctor` uses the same former-source identity checks as `oms remove` to distinguish verified former checkouts from unidentified paths. Doctor reports both categories without changing either and does not probe origin reachability to establish identity.

Complete preflight for the entire selection before removing anything. The plan shows the local branches and tags that will disappear, defaults to No in a terminal, and requires `--yes` for unattended normal removal. `--force` permits discarding staged, unstaged, untracked, and ignored working files only. A stash, in-progress Git operation, linked worktree (including outside `.oms-tree/`), or known unrecoverable history blocks deletion. Recheck the approved target state before each deletion; if it changes, stop, report completed and unattempted targets, and do not claim rollback.

For normal removal, obtain current refs and ancestry evidence from the declared origin without updating the source checkout's refs or files. Compare each local branch tip against commits reachable from current remote refs; do not require the same branch name. Compare tags by name and exact object, not by peeled commit. Account for a detached HEAD and other retained local history as well. Do not treat stale tracking refs as current proof. A successful remote inspection that leaves recoverability unproven blocks removal.

Check commits reachable from reflog entries but not from any current checkout ref or HEAD. Use the same current-origin ancestry evidence as for normal removal. If any reflog-only commit lacks proof of recoverability, report its object ID and advise preserving it outside the checkout before retrying. If origin is inaccessible, this blocker prevents the typed-alias exception even when every other check passes.

Distinguish origin access failure from a successful inspection that shows missing history. When access fails, block deletion if a branch has commits absent from its last known upstream from that origin. A branch with no configured upstream is not, by itself, evidence of unpublished history. Cached refs do not prove current recoverability. Only when access failure is the sole remaining blocker may an interactive invocation with one explicitly named alias offer the exception. Warn that the checkout may be the only remaining copy and require the exact alias. Do not offer the exception for `--all`, multi-alias selection, or unattended execution. Neither `--yes` nor `--force` can approve it.

### Make migration a separate plan-and-apply operation

`oms migrate` always plans the entire workspace; reject alias arguments before preview or application. `oms migrate --dry-run` prints the same plan without writing. Interactive application defaults to No; non-interactive application requires `--yes`. List the affected aliases, local Git directories, linked worktrees, shared root edits, and blockers. Redact credentials. Acquire a migration lock and revalidate the plan before writing. The lock does not cover other Git or IDE processes, so do not run them against affected paths during application.

Preflight every target and the shared root edits before starting the journal or moving anything. One blocked target rejects the whole plan. Only a failure or interruption after application starts enters journal-based recovery.

Identify legacy ownership from the declaration and agreeing Git evidence: the OMS alias path, the root's old gitlink and `.gitmodules` registration, and the checkout gitfile or expected Git directory. After the shared conversion commit, require local root history showing the registration's removal along with the retained Git data. Do not add a persistent migration receipt to shared files. A directory name or matching remote alone is insufficient. If a shallow clone lacks the required history, report how to retrieve it; until then, both migration and clone preserve the retained data and do not provision that alias. If both the checkout and local legacy data are absent after root conversion, `oms clone` can provision the source. An unfinished legacy root transaction blocks conversion until recovered with the previous CLI; do not interpret it as a migration journal.

Keep each initialized checkout in place. If it already owns a self-contained `.git` directory, validate and retain it. For an absorbed submodule, relocate its verified Git directory to `oms/<alias>/.git`, replace the old gitfile, and remove only the obsolete `core.worktree` binding if present. Preserve objects, refs, HEAD, index, and repository configuration; do not reset or re-clone. Inventory all Git worktrees before relocation, then use `git worktree repair` with their verified paths, including paths outside `.oms-tree/`. Verify that each worktree still resolves to the same repository data and keeps its branch or detached commit and index. Stop before writing when an unsupported configuration, a foreign path, an unresolved link, an in-progress Git operation, or shared ownership prevents a provably safe move. If the worktree directory is gone but verified legacy Git data remains, recreate the canonical directory only if it is empty or absent and the retained index can safely populate it without changing HEAD or the index. Report that missing working files cannot be reconstructed from Git. Moving repository data instead of cloning or exporting branches preserves local history, the stash, and worktree links.

Complete local conversion before applying shared root edits. Remove only matching OMS gitlinks from the index and OMS-owned sections from `.gitmodules` and root-local submodule configuration. Remove `autoCommitRegistration` from `oms.yaml` and add alias-specific shared ignore rules. Preserve unrelated sections, files, and index entries. Refuse overlapping edits to the root paths migration must change if they cannot be preserved; recheck the affected inputs and use Git index locking for index updates. Leave shared changes for the user to review and commit. If the root conversion commit is already present, finish only the local work; do not restore missing registrations or produce another root change.

Persist a migration journal under the verified root Git directory before the first move. Record the affected paths, checked identities, and enough original link/configuration and root-patch state to reconcile interruptions. On rerun, inspect the actual paths and resume only when they match a recorded state; do not overwrite data, restore an old index wholesale, or remove the only usable Git directory. Keep normal source commands from acting on a checkout involved in an incomplete migration. Clear the journal only after verifying the independent checkout, linked worktrees, and exact root changes. If evidence no longer matches, preserve both the data and journal and print the affected paths and recovery action.

### Remove the old interfaces at the major release

Use status JSON `schemaVersion: 2`. Remove `repos[].pin` and `root.submodulePointers`; keep unrelated field meanings and tree reporting. Update version-matched help and the shipped agent guidance together. Replace `oms sync` and `oms unsync` with `oms clone` and `oms remove`, without compatibility aliases. Remove `oms record`, the pointer skill, registration commit flags, and the legacy setting from normal parsing; only migration reads legacy topology and settings. Delete the general root transaction and pointer workflow once their callers are gone. Use a major Changeset targeting `3.0.0`; publication remains a separate maintainer operation.

## Risks / Trade-offs

- [Two computers have different local state] → The shared migration commit fixes only the root layout. Document per-computer previews and local conversion, including the old Git directory still present after pulling the new root.
- [Moving Git data can temporarily break worktree links] → Require a verified worktree inventory, persist the journal before relocation, verify links after repair, and block normal commands on partially converted checkouts.
- [Concurrent changes can invalidate the plan] → Use the migration lock and recheck root inputs and source identities at each write boundary; do not promise transactional rollback across unrelated Git processes.
- [Origin access may be lost permanently] → Normal removal stops without current evidence. A single named checkout can be removed after a separate typed warning only when origin access is the sole blocker.
- [Root revisions no longer pin a source version set] → Document that rollback of the root commit alone is not a source rollback. Keep historical revisions untouched and use a separate checkout if a user needs to reproduce one.

## Migration Plan

1. Test the conversion against local Git fixtures: dirty and detached sources, unpublished refs and stash, managed and external worktrees, unrelated staged root changes and submodules, interruption before and after relocation, and a second computer with local Git data after integrating the converted root.
2. On one computer, preview and apply migration, inspect the isolated root changes, then commit and push them explicitly. Do not run `oms remove` as a migration step.
3. On the other computers, run `oms migrate --dry-run` and safeguard local work before integrating the shared migration commit when possible. If the commit is already present, use `oms migrate` for the retained data; missing uncommitted files cannot be reconstructed. If root history is missing, obtain it before retrying. Use `oms clone` only for sources with neither a checkout nor local legacy data.
4. Before sharing the root changes, use the journal-guided recovery path to repair an interrupted conversion; never restore the root or replace source Git data blindly. After sharing, do not revert the root commit as an automatic downgrade. Users who need the pre-migration setup should check out the old root separately and leave converted checkouts and their local work intact.
