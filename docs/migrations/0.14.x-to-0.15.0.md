# Migrating from oh-my-space 0.14.x to 0.15.0

0.14.x left root topology changes unstaged after `oms sync` and `oms unsync`. A topology commit happened only if you passed `--commit` or accepted an interactive prompt — and that prompt appeared **only when stdin was a terminal**. In a pipe or a CI job the prompt was skipped silently, the topology stayed unstaged, and the command still exited 0. The same repository state produced different results depending on the terminal, and the job was left half-finished: `oms status` would then tell you to run `oms sync <alias> --commit`.

0.15.0 makes the topology commit **the default**, decided identically whether or not stdin is a terminal.

This is a finalization-behavior change only. Your submodules and the on-disk layout are untouched — no re-sync is required. Note that the commit itself includes `oms.yaml`; see below.

## Breaking change

`oms sync` and `oms unsync` now create the root topology commit by default. If you relied on the changes being left unstaged, add `--no-commit`.

| 0.14.x | 0.15.0 equivalent |
| --- | --- |
| `oms sync <alias>` | `oms sync <alias> --no-commit` |
| `oms sync --all` | `oms sync --all --no-commit` |
| `oms unsync <alias>` | `oms unsync <alias> --no-commit` |
| `oms unsync --all` | `oms unsync --all --no-commit` |

If you were already passing `--commit`, or accepting the prompt, **nothing changes** — leave those invocations alone.

The interactive "Create a root topology commit?" prompt is removed. It defaulted to Yes, so accepting it was the normal path and is now what happens without the prompt.

### The commit consumes your whole working-tree `oms.yaml`

A topology commit has always included the complete current `oms.yaml`, not just the aliases being synced — but in 0.14.x that only happened when you passed `--commit` or accepted the prompt. Now it happens by default, so an unrelated in-progress manifest edit gets swept into the commit:

```sh
# oms.yaml already has an unfinished `web` entry you were still editing
oms sync api        # commits .gitmodules, oms/api, AND the whole oms.yaml
```

If you keep uncommitted `oms.yaml` edits while syncing, use `--no-commit` and stage the manifest yourself.

### The one workflow that needs attention

Batching several syncs into a single hand-authored commit no longer works, because each invocation now commits:

```sh
# 0.14.x — one commit for both
oms sync api
oms sync web
git commit -m "chore: add api and web"
```

Two options:

```sh
# Let OMS produce the single commit it already knows how to make
oms sync api web            # → one "chore(oms): add submodules" commit

# Or keep hand-authoring it
oms sync api --no-commit
oms sync web --no-commit
git add -A && git commit -m "chore: add api and web"
```

## What stays the same

- **`--commit` still works.** It is accepted for compatibility and produces exactly the default behavior, so existing scripts and CI that pass it need no change.
- Every safety refusal is unchanged: partial removal topology is still rejected, an unsync commit still refuses unrelated staged root paths, a partially failed unsync still leaves successful topology unstaged, and a partially failed sync still finalizes only the successful aliases through the temporary index.
- The commit messages are unchanged (`chore(oms): add api submodule`, `chore(oms): add submodules`, and the `remove` equivalents), as are the path-limited commit, the temporary-index isolation, and the interrupted-commit recovery preflight.
- All other commands are unchanged.

## Fixed by this change

`oms branch list <alias>` on an alias declared in `oms.yaml` but not yet registered would offer to sync it, succeed once, and then **fail on the very next invocation** with `root gitlink and .gitmodules registration are inconsistent or pending addition/removal`. The delegated sync left the topology unstaged, which put the alias into a partially-registered state that `oms branch list` refuses.

Now the delegated sync commits its topology, so the alias ends up fully registered and repeating the command works.
