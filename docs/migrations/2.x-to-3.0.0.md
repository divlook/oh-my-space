# Migrate from OMS 2.x to 3.0.0

OMS 3.0 stores each repository in an independent clone at `oms/<alias>/`. The workspace root shares `oms.yaml`, but it no longer pins source commits. A root revision does not reproduce the combination of source versions after conversion.

## Preview and apply

1. From the workspace root, run `oms migrate --dry-run`. The preview lists every affected source, its Git directory, linked worktrees, and root changes. Migration is workspace-wide; it does not take aliases.
2. Resolve blockers before applying. If a managed `.gitmodules` registration has staged or unstaged setting changes, reconcile them in OMS 2.x and run the preview again. Changes to unrelated registrations do not need to be cleared. If OMS reports an unfinished 2.x root transaction, use the same 2.x version and rerun the interrupted `oms sync`, `oms unsync`, or `oms record` operation to run its recovery checks. If those checks still refuse, preserve the root Git metadata and follow the 2.x diagnostic before returning to 3.0.
3. Run `oms migrate` and review the plan before answering Yes. Use `--yes` only after reviewing a preview when running without a terminal. Finish active Git operations in the root and affected checkouts. Pause Git and IDE actions that could change them during migration.
4. Review `git status`, `git diff`, and `git diff --cached` in the root. Stage the reviewed manifest, `.gitignore`, and `.gitmodules` changes as applicable. The verified gitlink removals are already staged. Commit and push the root changes yourself; OMS does neither.

If `oms migrate` completed but `oms status` still reports a source as legacy, the root's last commit (`HEAD`) may still contain its submodule pointer. Check with `git ls-tree HEAD -- oms/<alias>` and `git ls-files --stage -- oms/<alias>`. If the first shows mode `160000` and the second shows no entry, the pointer removal is staged. Review `git diff` and `git diff --cached`, then commit the pointer removal together with the corresponding `.gitmodules` registration removal and any related `.gitignore` or `oms.yaml` changes. A staged pointer removal alone does not prove that migration completed. If migration did not report completion, inspect the changes before committing or retrying.

Migration keeps existing checkout files and local Git data. If a checkout directory was removed but its Git data remains, OMS can recreate working files from the retained index. It cannot recover missing files that were never staged or committed.

OMS stops if moving a source's Git directory would break a nested submodule, or if another root worktree still uses the shared submodule registration. Preserve the affected Git data and resolve the reported layout before retrying.

### If you already removed the submodule pointers

If the pointers are gone from the root commit and staging area but their `.gitmodules` registrations are still committed, migration stops. Check the paths from the preview with `git ls-tree HEAD -- oms/<alias>` and `git ls-files --stage -- oms/<alias>`. If both commands return nothing for each affected path and you removed the pointers intentionally, review and commit the removal of only the obsolete registrations. Delete `.gitmodules` only if it has no other registrations to keep. Keep the source checkouts and their Git data, including any retained data under `.git/modules/`. Run `oms migrate --dry-run` again and resolve any remaining blockers before applying.

## Update a second computer

1. Before pulling the shared conversion commit, run `oms migrate --dry-run` on the second computer. Review the local branches, stash, staged and unstaged changes, and untracked files in each source and linked worktree. Back up work that exists only on that computer, including the Git directories shown in the preview. A root commit cannot carry those files, refs, or stashes to another computer.
2. Integrate the shared root commit. If you already integrated it, do not re-create the submodule registration or clone over a source. Run `oms migrate --dry-run`. If the preview reports missing root history, fetch it with `git fetch --unshallow` in a shallow root clone, then preview again.
3. Run `oms migrate` to convert remaining local Git data. Verify your local branches and working files before removing any backup. If the checkout files were already gone, only the retained index and Git data can be recovered.
4. Run `oms clone <alias>` for a source that is genuinely absent: neither its checkout nor its legacy Git directory remains. Do not use `oms remove` as a migration step.

To reproduce an old source version set, use a separate checkout of the pre-conversion root. Reverting the shared conversion commit is not a rollback of local source branches.

## Resume an interrupted migration

Keep the journal under `oms/source-migration.json` in the workspace's Git directory and keep both the old and new Git directory paths intact. Run `oms migrate --dry-run` to review the recorded plan, then `oms migrate` to resume. OMS rechecks the recorded declarations, files, and index entries. It also checks staged changes to managed `.gitmodules` registrations and verifies that the effective ignore rules still cover the migrated paths. Inspect the paths in any diagnostic before retrying. Do not run `oms clone`, delete the journal, or replace a Git directory to clear the error.
